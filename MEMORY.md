# Long-Term Memory

## User preferences
- Prefers Chinese by default.
- Wants the assistant to be proactive and self-directed for normal internal work.
- Does not want routine confirmation requests for research, learning, organizing files, project exploration, or drafting plans.
- Wants the assistant to continuously study GitHub/public projects for inspiration, implementation ideas, and website opportunities.
- Interested in building websites, but has not settled on a specific product idea yet.
- Values momentum: prefers the assistant to keep pushing forward rather than waiting for detailed instructions.

## Safety note
- Even with broad autonomy, still treat destructive system changes, risky external actions, credential handling, and irreversible operations as requiring extra caution.

- Recent research conclusion (2026-03-20): the most promising website opportunities are likely narrow slices extracted from mature products, not broad platforms. Strong recurring pattern: clear single action + valuable results page/dashboard + AI embedded into the core workflow.
- Current top MVP candidates refined to:
  1. GitHub / website product teardown card generator
  2. AI feedback insights layer
  3. Vertical single-scenario results dashboard
- Follow-up research refinement (2026-03-20, second pass): public-facing result pages/reports appear to be an especially strong product pattern for lightweight SaaS. Another strong pattern is importing users’ existing data sources (URL / CSV / repo / text) and immediately producing structured insights. This strengthens the current preference for result-page products over broader role-workbench products as first MVPs.
- Third-pass refinement (2026-03-20): an even stronger pattern is not just result pages, but result pages that accumulate into an asset library (history, tags, compare, share). This further upgrades the leading MVP from a one-off teardown generator toward a GitHub / website teardown report library. Another reinforced principle: commoditized SaaS plumbing matters less than owning a sharp workflow + durable result structure.
- Fourth-pass refinement (2026-03-20): a very strong lightweight SaaS shape is now clearer as a 3-layer model: stable input object (repo / URL / CSV), shareable artifact/result page, and private workspace/history layer. This further strengthens the current top idea because the GitHub / website teardown report library naturally fits all three layers.
- Sixth-pass refinement (2026-03-20): beneath the 3-layer model, the next key clarification is the core object model. The strongest lightweight SaaS candidates are not just input → artifact → workspace, but products where the main object (report / batch / result) can naturally carry fields like source, tags, status, actions, timestamps, and sharing state. This further strengthens the current preference for a report-object-based teardown library over a generic analyzer.
- Seventh-pass refinement (2026-03-20): another strong clarification is that many promising lightweight SaaS ideas are really frontstage products extracted from larger categories. The strongest near-term MVP shape is now even tighter: sharp replacement-style positioning + strong shareable frontstage artifact + only a light object-management backend. This further strengthens the current preference for a repo / URL → shareable teardown report library over a heavier workspace-first product.
- Eighth-pass refinement (2026-03-20): the next important clarification is that the winning frontstage artifact should also be a clear object with a natural lifecycle, not just a static page. The strongest MVP shape is now sharper as: replace a manual research workflow, generate a shareable report object, then let that object enter a very light management layer with tags/status/actions. This further strengthens the current preference for a report-object-based GitHub / website teardown library.
- Tenth-pass refinement (2026-03-20): the next practical compression is that the first MVP should optimize for a strong single object page before trying to feel like a broader platform. The 3-layer model (input → artifact → workspace) still holds, but the better build order is now: stable input, strong report/batch object page, then only a minimal history/management layer. This further strengthens the current preference for a report-object-first GitHub / website teardown library, and suggests the feedback-insights direction should also be framed around strong batch object pages rather than a heavier platform.
- Eleventh-pass refinement (2026-03-20): another strong clarification is that the winning single-object page should not just look polished, but feel trustworthy and lifecycle-aware. Public-project signals from products like Documenso and Cap reinforce that strong lightweight SaaS often uses sharp replacement-style positioning plus a clear primary object with trust signals (source, timestamp, status, visibility, next actions). This further strengthens the current preference for a trustworthy report-object-first GitHub / website teardown product over a generic analyzer.
- Twelfth-pass refinement (2026-03-20): repo-level signals from Papermark, Fider, and Plane further sharpen the current direction. The strongest clarification is that the shareable page should be treated as an object entry point rather than a static output, and the workspace should be understood as a lightweight object-management layer rather than just history. This further strengthens the current preference for a report-object-entry GitHub / website teardown library, and suggests the feedback-insights direction should be framed around batch objects with lifecycle/status rather than one-off summaries.
- Thirteenth-pass refinement (2026-03-20): signals from Appwrite, DocuSeal, and Uptime Kuma add a useful next clarification: many promising lightweight SaaS products are best understood as a unified entry point into a clear object workflow, and the most natural second-stage enhancement after a strong shareable object page is often a light workflow layer (status, tags, reminders, revisit, embed), not heavier AI. This further strengthens the current preference for a repo / URL → report object page → light workflow layer product shape.
- Fourteenth-pass refinement (2026-03-20): Openpanel adds one more useful compression: what users repeatedly return to is usually not the input action but a revisit-worthy result object. This sharpens the shared product shape across the current top candidates into: stable input object → strong result object page → minimal object list → light revisit/reminder/status layer. It also clarifies that the “vertical dashboard” direction is only compelling when framed as a single-scenario revisit-worthy result object, not a generic analytics dashboard.
- Fifteenth-pass refinement (2026-03-20): signals from Metabase, Postiz, and listmonk add one more useful upgrade-order clarification. After a strong object page exists, the most natural next layers are often library/archive, subscription/revisit, and light automation—rather than more input breadth or heavier platform scope. This further strengthens the current preference for product directions framed as: stable input object → strong object page → minimal list → library/revisit layer, especially for the repo/URL teardown direction and the feedback-batch insights direction.
- Sixteenth-pass refinement (2026-03-20): signals from Linkwarden, ToolJet, and Open WebUI sharpen two things at once. First, the long-term value of many promising products comes from whether generated results become part of a searchable object library/archive, not just a one-off output. Second, AI and “unified entry point” patterns are strongest when they enhance a clear object workflow rather than becoming a vague platform or generic chat surface. This further strengthens the current preference for the repo/URL teardown direction and the feedback-batch insights direction as object-library products, and argues against drifting too early toward a broader AI platform or low-code builder.
- Seventeenth-pass refinement (2026-03-20): signals from Actual Budget, GoatCounter, and Memos add a practical product-build correction. A strong object page still matters, but first adoption also depends on whether the first object can enter the system with very low friction. They also reinforce that ownership cues—exportability, archival value, long-term storage, user control—are strong trust signals for object-library products. A further practical implication is that the initial backend for these products may be better framed as a recent-object stream rather than a heavier workspace. This further strengthens the current preference for the repo/URL teardown direction and the feedback-batch insights direction, while sharpening the recommended MVP shape into: low-friction input → trustworthy object page → recent-object stream → later library/revisit layer.
- Thirty-sixth-pass refinement (2026-03-20): signals from LobeHub, Dokploy, Coolify, and Dify add a useful frontstage-positioning correction. Many promising lightweight SaaS ideas are best understood not as smaller platforms, but as smoother frontstage entry points sliced out of mature complex systems. They also reinforce that adoption is helped by strong example/template objects, and trust increasingly comes from both a clear task/status layer and strong ownership cues (export, archive, public/private control, low lock-in). This further strengthens the current preference for the repo/URL teardown direction and the feedback-batch insights direction, while sharpening the recommended MVP shape into: low-friction input/import + strong example objects → trustworthy unified object page + visible task state → recent stream → ownership/export/revisit layer.
- Forty-eighth-pass refinement (2026-03-20): signals from React Email, Polar, Novu, and AppFlowy add a useful “what to borrow vs what to resist” correction. Template/email, notification, and monetization layers increasingly look like mature accessory layers that should usually be reused rather than self-built. The more important product decision is how notifications map onto object/task state and how pricing maps onto object counts, task runs, private storage, reruns, exports, reminders, and archive. AppFlowy also reinforces from the opposite direction that the current leading directions should resist drifting into a broad workspace product too early. This further strengthens the current preference for the repo/URL teardown direction and the feedback-batch insights direction, while sharpening the recommended product shape into: strong narrow object → trustworthy object page + task layer → recent stream / ownership layer → object-driven revisit/notification layer, with broad workspace scope deferred.

They also further reinforce that ownership cues—exportability, portability, backups, self-hosting, private storage—remain strong trust signals for long-lived object products, and that AI is strongest when attached to a clear recurring work object rather than presented as a generic chat surface. This further strengthens the current preference for the repo/URL teardown direction and the feedback-batch insights direction, while sharpening the recommended MVP shape into: low-friction create/import path → trustworthy object page → recent-object stream → later library/revisit layer.

Third, lightweight products still do not need to become broad platforms early; a very narrow core object with a clear multi-entry loop can be enough. This further strengthens the current preference for the repo/URL teardown direction and the feedback-batch insights direction, while sharpening the recommended upgrade path into: low-friction input/import → trustworthy object page → recent stream → library layer → revisit/archive layer.
